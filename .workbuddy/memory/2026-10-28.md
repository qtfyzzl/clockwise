## 烧录受阻：成品板不支持自动进下载模式

- 用户插上板子后检测到 **COM6 / USB-SERIAL CH340**（`VID:PID=1A86:7523`）。

- 结论：**成品 PCB 没有把 CH340 的 DTR/RTS 接到 ESP32 的 EN/IO0**（省两个三极管），自动复位进不了 bootloader，必须手动拉低 IO0。

  - 串口确认：`boot:0x3` + `waiting for download` 才对；`boot:0x13` 是普通启动。
  - 失败对照表（0x13 / No serial data / Could not open port / MD5 mismatch）。
- 交付 `dist/flash-wait.bat`：每 2 秒用 `esptool chip-id` 探测，一旦进下载模式自动烧 460800，失败回落 115200。解决"按完键要赶紧敲命令"的时序焦虑。

### 关键突破：必须是 --before no-reset，且不能先探测

排查出两个叠加的坑（12:25 实测）：

1. **`chip-id` 探测成功后，esptool 默认 `--after hard-reset` 会把芯片踢出 bootloader**，紧接着的 `write-flash --before no-reset` 就报 `No serial data received`。
   → 正确做法：**不做探测**，直接循环跑 `write-flash --before no-reset`。
2. **`write-flash` 默认 `--before default-reset` 会复位芯片**；这块成品板 `-- RTS→EN 接了、DTR→IO0 没接 --`，复位后 IO0 为高 → 芯片又正常启动 → 报 `Wrong boot mode detected (0x13)`。手动按键进的下载模式被这一步直接作废。
   → 烧录命令模板：
   ```
   esptool --chip esp32 --port COM6 --before no-reset --baud 460800 write-flash -z 0x0 <merged.bin>
   ```
- 诊断结论：这块成品板 **EN 接了、IO0 没接**（否则不会出现"复位后报 0x13"这一现象），所以自动进下载模式在硬件上就不可能，必须每次手动按住 BOOT。
- 待办：`dist/flash-wait.bat` 和 README 里的命令**都要加上 `--before no-reset` 并去掉 chip-id 探测**，否则用户自己烧时还会踩同样的坑。

### 修正（12:29，用户暂停，尚未烧成功）
上面对 `--before no-reset` 的结论**是错的**，实测 25 次 + 40 次循环全失败（`No serial data received`）。真正机制：
- 这块板 **RTS→EN 有接、DTR→IO0 没接**。打开串口时 RTS 常态可能把 EN 拉住，`no-reset` 就永远等不到 bootloader。
- 而 `default-reset` 会复位一次 EN，**但如果用户已经松开 BOOT，IO0 为高** → 芯片正常启动 → 0x13。
- **正确组合：让用户"一直按住 BOOT 不松手" + 用默认复位模式**，由 esptool 做那次复位，IO0 恰好被按住。我上一条建议的"按 BOOT→点 EN→松开 BOOT"在这块板子上必然失效。
- 用户 12:29 叫停（"暂停"），尚未烧成功。`platformio.ini` 里我加的 `upload_flags = --before no-reset` **待改**（大概率应去掉，改成让用户按住 BOOT + 默认复位）。
- 教训：不要在没有实测成功前把排障结论写死进配置文件。

### 重大发现（12:30，串口实证）：flash 里的 app 已被清零，设备在 bootloop

监听 COM6 抓到 207 行，反复循环：

```
rst:0x1 (POWERON_RESET),boot:0x13 (SPI_FAST_FLASH_BOOT)
E (488) esp_image: invalid segment length 0xffffffff
E (488) boot: OTA app partition slot 0 is not bootable
E (488) boot: No bootable app partitions in the partition table
ets Jul 29 2019 12:21:46
rst:0x3 (SW_RESET),boot:0x13 ...
```

- `0xffffffff` = 擦除态，**app 分区是空的**，分区表还在但 app 不可引导 → 芯片反复 SW_RESET。
- 用户看到的「LED 一直闪红点」就是这个 bootloop（不是按键问题，也不是供电问题）。
- 说明之前某次 `write-flash` 已经执行了擦除但没写成功，把原固件搞没了。**必须烧回去才能恢复。**
- 好消息：ROM bootloader 正常，串口能打印，芯片没坏；RTS 不会把 EN 拉住（开串口时芯片仍在 bootloop，说明 EN 未被占用）。
- 结论：只要 IO0 在复位瞬间为低就能进下载模式。BOOT 按键未必接 IO0（用户按了无效）→ **改用物理短接 IO0–GND**，然后拔插 USB 上电，bootloader 会停住等待。
- 已启动 50 次 `--before no-reset` 循环等待短接（task ksgtUP），短接 + 上电后应能直接烧进去。

三种组合共跑了 120 次，定论：

| 组合 | 结果 | 原因 |
|---|---|---|
| 默认复位 + 用户「按一下松开」 | `0x13` ×45 | 松手太早，复位瞬间 IO0 已高 |
| `--before no-reset` + 按键 | `No serial data` ×50 | 不复位，芯片自己 bootloop，永远抓不到 bootloader |

| **默认复位 + IO0 持续短接** | 唯一可行（尚未验证成功） | 复位瞬间 IO0 低 |

- **硬件定论：CH340 的 RTS→EN 已接（每次都能成功复位并读回 boot 值），DTR→IO0 未接（恒为 boot:0x13，从未出现 0x3）**。所以自动进下载模式在这块板上物理不可能，只能手动拉低 IO0。

## 16:0x 修复 WiFi 乱码 + 自动亮度失效

### 问题 1：设置页 WiFi 名乱码（页面 charset 修不了）
- 根因：**SSID 走 HTTP 响应头**（`X-wifiSsid`），而 HTTP 头按规范只能 latin1。浏览器把 UTF-8 字节当单字节解码 → `å¼ å­ççèé¾16`。之前只在 HTML 里加 charset 是没用的，因为数据根本不走 body。
- 修复：`CWWebServer.h` 新增 `ClockwiseWebServer::urlEncode()`（只保留 `alnum - _ . ~`，其余 percent 编码），所有字符串类参数（timeZone/wifiSsid/ntpServer/canvasFile/canvasServer/manualPosix）出站前编码；前端 `splitHeaders` 里 `dec()` 用 `decodeURIComponent` 还原。
- 验证：node 复刻编码器，4 个用例往返一致；旧行为复现出与用户截图一致的乱码；纯 ASCII 值（time.google.com）编码后无变化。

### 问题 2：自动亮度完全不工作
- 根因：`autoBrightEnabled = (autoBrightMax > 0)`，而 **NVS 被 merge-bin 清空后 autoBrightMax=0** → 功能整体关闭，跟"房间多暗"无关。
- 顺带修掉 `automaticBrightControl()` 三个缺陷：
  1. **只有上限钳位、没有下限**：Arduino `map()` 不检查边界，读数 < ldrMin 时算出 0/负数，强转 uint8_t 回绕成很大的值 → 亮度乱跳。改为双端钳位。
  2. `ldrMax <= ldrMin` 除零/异常 → 直接按亮度上限处理。
  3. 迟滞比较 `abs(currentBrightSlot - slot)` 统一转 int，避免 uint8_t 相减回绕。
- 提取 `#define AUTO_BRIGHT_SLOT_MAX 10`；默认值 `autoBrightMax` 0 → **800**（GL5539+10k 实测推荐）。
- 验证（node 复刻同一套整数语义）：ADC 40→亮度4、200→10、400→16、600→22、800+→32；0..4095 全区间**单调递增 PASS**；低于下限不再回绕；阈值无效时回落到上限。

### 问题 3：烧录会清 NVS → 已改默认烧录方式
- `merge-bin` 从 0x0 连续以 0xFF 填充，会覆盖 NVS(0x9000-0xDFFF) → 每次烧录都重置配置。
- `dist/flash.ps1` 改为**默认分段烧录**：bootloader@0x1000 / partitions@0x8000 / boot_app0@0xe000 / app@0x10000。partitions.bin 仅 3KB(0x8000-0x8BFF)、boot_app0 在 0xE000(otadata)，**都不碰 NVS** → WiFi/时区/亮度保留。
- 新增 `-Merged` 开关（救砖/量产用），`-Erase` 保留。
- ⚠️ 因为 NVS 里现存的 `autoBrightMax` 仍是 0，**分段烧录后自动亮度依然关闭**，需要在设置页把「最大值」填 800（前提：不想重配 WiFi），或用 `-Erase` 让新默认值生效。

### 三个必须知道的 Canvas bug（上游都有）
1. **启动崩溃**：`PNGRender.h` 里 `static PNG png;` 占 **48,156 字节 .bss**（PNGdec 把 `ucZLIB[32768+…]`、调色板、像素行、文件缓冲全塞在结构体里，注释写"避免 malloc"）。静态内存 52KB→101KB，ESP-IDF 启动时 `xTaskCreatePinnedToCore` 失败 →
   `assert failed: esp_startup_start_app app_startup.c:86 (res == pdTRUE)` 无限重启。
   用 `xtensa-esp32-elf-nm --size-sort` 才定位到（`_ZL3png` 48156）。
2. **图片全废**：把 png 改成堆分配后启动好了，但 `new PNG()` 申请 48KB 失败（32KB JSON doc 在静态初始化阶段先挖走一块，WiFi 再切碎堆）→ `PNG 缓冲分配失败（堆不足）`，文字/图形能画、图片和精灵全丢。

   结果：`PNG 缓冲就绪 size=48156 free=142556`。
3. **GitHub 拉不到**：设备访问 `raw.githubusercontent.com` 报 `Connection failed`（PC 上 curl 200，但 ESP32 的 mbedtls 握手被网络中间设备 reset；NTP/UDP 正常）。

## 21:0x 代码审查：找到「进不去设置页」的真凶（关键）

**根因不是 WiFi 省电、不是热点、不是防火墙**，而是 `CWWebServer.h` 的 `handleHttpRequest()`：

```cpp
while (client.connected())      // 没有超时
{
  if (client.available()) { ... if (c=='\n') break; }
}
```

只要客户端**连上但不发完整请求行**（浏览器预连接、curl --max-time 中断、端口扫描、我自己那些 `socket.create_connection` 探测），`connected()` 恒 true、`available()` 恒 0 → **死循环卡死 loop()**。lwIP 在独立任务里，所以 ping 仍通、但 HTTP 永不响应、屏幕冻结、只能复位恢复。

→ 这一条解释了全部现象：**"ping 通但进不去设置页"、"reboot 后好一会儿又坏"、以及被我自己的探测打断**。
→ 之前误判为 WiFi modem sleep（加了 `WiFi.setSleep(false)`，无效但无害，保留）。

### 本轮修掉 5 个问题
1. **[严重] HTTP 读循环无超时** → 加 2s `requestDeadline` + 空转 `delay(1)` + 超时清 buffer
2. **[严重] 自动换盘只生效一次** → `getFormattedTime("z")` 在 ezTime 里是**时区缩写**，`toInt()` 恒 0 → 改 `"Ymd"` 字符串去重
3. **删除当前主题后 canvasFile 悬空** → 加 `firstLocalTheme()` 自动切换
4. **`client.setTimeout(5)` 单位是毫秒** → 5ms 读请求头必超时，改 1000ms
5. **`/theme` 响应体多 2 字节** → 去掉 body 后的 `client.println()`
6. 顺手：`uint8_t method_pos/path_pos` → `int`（长 URL 索引溢出），并加合法性判断

## 流动字主题「长春光华学院 电信张明达」（贪吃蛇式滚动）

交付：`canvas/snake-text.json`（39 帧帧动画，64×22 索引 PNG，JSON 12.2KB / 16384 上限，单帧 ≤228B）。
生成器：`editor/make_snake_text.py`（simhei 12px 逐字栅格化 + 正弦纵向起伏 amp=3 / λ=156 + 平铺切窗）；预览 `canvas/snake-text-preview.gif`（39 帧 × 50ms，与真机同速）。

### 固件硬约束（这次逐行读出来的，务必记住）

1. **`renderImage(const char*, uint8_t x, uint8_t y)`**：精灵坐标 int8_t → 传进 uint8_t。**x<0 会回绕成 200+ → 整块精灵不可见**（不是左裁，是整块消失）。所以「向左滚出屏」的位移方案根本不可行。
2. 位移启用条件 `moveTargetX > -1 || moveTargetY > -1`：负目标当未设置。想负向位移只能靠把 `moveTargetY` 设成非负来"骗过"判定。
3. `handleSpriteAnimation` 的帧推进条件是 `_currentFrameCount < totalFrames`：**单帧精灵每 loopDelay 才推进一次**，所以靠位移做动画时 loopDelay/frameDelay 必须很小（约 10ms），否则一步跨太大、擦除矩形会吃掉相邻精灵。
4. 擦除矩形 = 旧∨新位置；右移回程会擦到左邻精灵右边缘（绘制顺序 0..N）。
5. **JSON 缓冲实际是 `DynamicJsonDocument doc(16384)`**（不是 HANDOFF 里写的 48KB，48KB 会挤爆 lwIP）。
6. `_currentFrameCount` 重置条件 `(currentSecond*1000) % loopDelay == 0` → loopDelay 必须是 1000 的因数/倍数（能整除），否则不重置。

### 采用方案：预渲染滚动帧（唯一能做出平滑单向流动的办法）

- 把整句按 12px 字宽 + 12px 间隔平铺成 PERIOD=156px 的长条，每 4px 切一个 64×22 窗口帧，共 39 帧。
- 单个 sprite，x=0/y=21 固定，`frameDelay=50`、`loopDelay=2000`，纯帧动画播放 → 连续左滚、无缝循环（实测 frame0→1 与末帧→0 的 4px 位移 mismatch 均为 0）。
- 颜色：蛇头「长」亮黄 (255,226,40)，其余荧光绿 (0,255,90)。
- 汉字无固件字体，必须预渲染 PNG；每帧按实际用色裁剪调色板（多为 1-bit），体积才压得住。
