# 原生模式 vs 画布模式：怎么选

> 面向图形编辑器的实现者。判断"这个主题该导出成哪种格式"看这份。
> 数据来自 31 个官方主题的实测（2026-10-29），不是估算。

---

## 一句话区别

**画布模式**把主题存成 JSON 文件放在闪存里，设备开机后**逐帧解码**渲染。
**原生模式**把画面编成 C 数组写进固件，设备**直接读取**绘制，不经过解码。

---

## 本质差异

| 维度 | 画布模式 | 原生模式 |
| --- | --- | --- |
| 存储形态 | JSON 文件 + base64 编码的 PNG | C 数组，RGB565 原始像素 |
| 存放位置 | 闪存（SPIFFS 分区 256 KB） | 固件（app 分区，当前余量 154 KB） |
| 容量上限 | **单主题 16 KB**（硬上限） | 受固件分区余量约束，当前约 154 KB |
| 单帧上限 | 解码后 4096 字节 | 无单帧限制，只受总量约束 |
| 渲染开销 | 每帧 base64 解码 + PNG 解压 | 无（内存映射区直读） |
| 修改方式 | 网页上传，**秒级生效** | 重新编译 + OTA 推送，**约 1 分钟** |
| 表达方式 | 声明式：帧序列 + 位移参数 | 命令式：任意 C++ 代码 |
| 可用元素 | `image` / `text` / `datetime` / `line` / `rect` / 精灵动画 | 任意：直线、圆、位图、字体、自定义算法 |
| 依赖 | 无（主题文件自带全部内容） | 需要重新烧录固件 |

---

## 容量换算（关键）

### 实测：每帧到底占多少字节

用真实 PNG 编码实测（16×32 一帧 = 1024 字节 RGB565），三类画面差异极大：

| 画面类型 | 每帧 base64 | 占 RGB565 | 每千像素 | 16 KB 能放 |
| --- | --- | --- | --- | --- |
| 大面积纯色 / 点阵字 | **128 B** | 12% | 250 B | **约 112 帧** |
| 有序渐变 | 176 B | 17% | 344 B | 约 81 帧 |
| 复杂像素画（多色块交错） | **452 B** | 44% | 883 B | **约 31 帧** |

同一尺寸下，复杂度造成 **3.5 倍**差异。所以"帧数多"不等于必须用原生——点阵字、纯色动图放一百多帧都装得下。

### 编辑器可直接用的公式

```
估算体积 = 帧数 × (帧宽 × 帧高 / 1000) × K + 2000
```

`K` 按画面类型取值：纯色 250 / 渐变 344 / 复杂像素画 883。`2000` 是 name、setup、loop 等固定字段的开销。

算出来 ≤ 16384 就能走画布。

### 官方主题实测对照

| 主题 | 帧数 | 每帧 base64 | JSON 体积 | 结果 |
| --- | --- | --- | --- | --- |
| pac-man | 6 | 140 B | 2.8 KB | ✅ 远低于上限 |
| christmassnoopy | 30 | 330 B | 13.5 KB | ✅ 刚好 |
| mario-1 | 66 | 431 B | 34.4 KB | ❌ 超一倍 |
| bugcat-1 | 14 | — | 40.3 KB | ❌ 主要体积在 setup 的大贴图 |

> 注意：`bugcat-1` 只有 14 帧却 40 KB，因为 setup 层还有几张大尺寸背景图。
> **估算时要把 setup 里的贴图一并计入**，不能只数精灵帧。

## 能力对照

| 需求 | 画布 | 原生 | 说明 |
| --- | --- | --- | --- |
| 帧序列动画 | ✅ | ✅ | 两者都支持，画布受 16 KB 限制 |
| 图片贴图 | ✅ | ✅ | 画布需 PNG + base64，原生直接数组 |
| 数字时钟 | ✅ | ✅ | 画布用 `datetime` 元素 |
| 固定文字 | ✅ | ✅ | 画布用 `text` 元素 |
| 直线 / 矩形 | ✅ | ✅ | 画布有 `line` / `rect` / `fillrect` |
| 圆形、多边形、弧线 | ❌ | ✅ | 画布只有上述五种元素 |
| 精灵沿路径移动 | ⚠️ 仅直线位移 | ✅ | 画布只支持水平/垂直位移 + 目标点 |
| 随机行为 | ❌ | ✅ | 画布没有随机能力 |
| 碰撞检测 | ❌ | ✅ | 需写代码 |
| 状态机（游戏逻辑） | ❌ | ✅ | 需写代码 |
| 按时间切换不同画面 | ⚠️ 有限 | ✅ | 画布只有 `datetime` 能取时间 |
| 自定义字体 | ⚠️ 四种内置 | ✅ | 可把任意字体编进固件 |
| 修改后立即生效 | ✅ 上传即用 | ❌ 需重烧 | 这是画布最大优势 |

## 判断标准（编辑器用）

按顺序判断，**第一个命中的就是答案**：

```
1. 需要随机 / 碰撞 / 状态机 / 圆形等画布没有的能力？
   └─ 是 → 原生

2. 估算 JSON 体积 > 16 KB？
   └─ 是 → 原生
   └─ 估算方式见下节公式：帧数 × (帧宽×帧高/1000) × K + 2000
      · 纯色/点阵字 K=250，渐变 K=344，复杂像素画 K=883

3. 用户需要频繁修改、上传即看到效果？
   └─ 是 → 画布

4. 帧率要求 ≥ 20 fps（帧间隔 ≤ 50 ms）？
   └─ 是 → 原生（画布每帧有解码开销，高速下容易掉帧）

5. 以上都没命中 → 画布
   └─ 体积小、纯帧序列、要能随时改，画布更合适
```

### 快速估算表

| 动画规格 | 估算体积 | 画布能否装下 |
| --- | --- | --- |
| 8 帧 16×32 纯色 | 3.0 KB | ✅ 轻松 |
| 40 帧 16×32 纯色 | 7.0 KB | ✅ 轻松 |
| 100 帧 16×32 纯色 | 14.5 KB | ⚠️ 临界 |
| 20 帧 16×32 像素画 | 10.8 KB | ✅ 轻松 |
| 31 帧 16×32 像素画 | 15.6 KB | ⚠️ 临界 |
| 40 帧 16×32 像素画 | 19.6 KB | ❌ 超限 |
| 10 帧 64×64 像素画 | 26.3 KB | ❌ 超限 |
| 20 帧 16×32 渐变 | 5.4 KB | ✅ 轻松 |
| 静态画面 + 数字时间 | 1–3 KB | ✅ 可以 |

## 典型场景

### 适合画布

- **纯帧序列**：动物摇头、烛光闪烁、雪花飘落（无逻辑，只是循环播帧）
- **静态画面 + 数字时间**：插画背景 + `datetime` 元素
- **文字类**：流动字、标语、日期显示
- **需要反复调整**：还在调试阶段、想边看效果边改

### 适合原生

- **帧数多**：60 帧以上的流畅动画（走路、跑步循环）
- **有逻辑**：随机生成、碰撞反弹、按键响应、按时间切换场景
- **复杂绘制**：圆形进度环、波形图、粒子效果
- **高帧率**：需要 20 fps 以上
- **首次烧录后不再改**：定稿的作品

## 编辑器该怎么输出

### 判断流程

```
用户在编辑器里做好动画
        ↓
统计：帧数、每帧尺寸、画面复杂度
        ↓
按上面「判断标准」估算 JSON 体积
        ↓
   ┌────┴────┐
   ≤ 16 KB    > 16 KB
   ↓          ↓
导出 JSON   提示用户：需要转原生
（直接上传） 提供"导出 C 数组"功能
```

### 两种导出产物

**画布导出**：`.json` 文件，符合 `canvas/theme.schema.json`，直接上传设备。

**原生导出**：生成 C 头文件，形如：

```c
// 16×32 的一帧，RGB565，按行优先
const unsigned short FRAME_00[512] = {
  0x0000, 0xFFFF, 0x0000, ...
};
```

再配一个 `Clockface` 类，实现 `setup()` 与 `update()` 按帧切换。

> 注意：原生主题需要重新编译固件，当前的编译产物已占 91% 分区，
> 每加一个主题约 11 KB。若要支持"编辑器直接导出原生主题"，
> 还需要配套的工程模板与编译脚本，这是下一步的工作。

### 给用户的提示语

当估算超限时，不要只说"太大了"，要给出可操作的选项：

> 这个动画需要约 28 KB，超过设备 16 KB 的上限。有三种处理方式：
> 1. **减少帧数**：66 帧压到 30 帧，配合帧间隔调整，观感差别不大
> 2. **缩小画面**：把 64×64 改成 32×32，体积降到四分之一
> 3. **转为原生主题**：不受体积限制，但需要重新编译固件（约 1 分钟）

## 附：为什么画布有 16 KB 上限

设备用 `DynamicJsonDocument(16384)` 解析主题。ArduinoJson 会把 JSON 里的**所有字符串复制一份**进内存池，包括 base64 图片。所以：

- 文件本身 16 KB → 解析时需要 16 KB 连续堆内存
- 而解析发生在 WiFi 启动之前，此时堆还没被切碎，能拿到大块
- 一旦超过 16 KB，要么解析失败，要么需要更大的池子——而更大的池子会和 WiFi 协议栈抢内存，实测会导致网络不可用

这是硬约束，不是可以调的参数。要在画布模式下承载更大主题，只能改存储形态（把图片外置成独立二进制文件），那是另一个层级的改造。
